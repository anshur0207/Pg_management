
# PG Manager

A multi-tenant PG and hostel management platform built with Next.js, TypeScript, Tailwind CSS, and Supabase.

## Current status

- Responsive public landing page, owner authentication, and a separate student portal.
- Supabase browser/server client setup for secure cookie-based sessions.
- PostgreSQL schema and RLS migrations are in `supabase/migrations/`.
- Owners can add properties and create email-bound, seven-day resident invitations. Students create accounts through those private links and get a resident dashboard.
- Student signup requires a valid invitation; the database links the invited email to its resident record and applies resident-scoped RLS.
- No demo properties, residents, or financial data are seeded.

## Getting started

1. Copy the Supabase Project URL and Publishable key into `.env.local` as `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (legacy anon keys may use `NEXT_PUBLIC_SUPABASE_ANON_KEY`). Never use the service-role key in browser variables.
2. In Supabase Auth → URL Configuration, set the local Site URL to `http://localhost:3000` and add your local/deployed `/auth/callback` and `/reset-password` redirect URLs.
3. Install/login to the Supabase CLI, link this directory to your project, and apply the schema with `supabase db push`. Linking/pushing requires a Supabase access token and database password; enter these only in the CLI prompts, not in `.env.local` or source control.
4. Run `npm install` and `npm run dev`.

Apply all migrations to the hosted project before using database-backed features. Authentication is enabled only when the project URL and public anon/publishable key are configured; the app does not simulate successful sign-in.

## Resident invoices and payments

- The database job creates one monthly rent invoice on the 2nd (02:00 UTC) for each current active stay. An active rent plan is used when it covers the billing month; otherwise the active occupancy rent, then resident rent, is used. The existing per-resident/per-month uniqueness constraint makes reruns safe.
- Owners can also create a manual invoice for a current resident, property, month, amount, and due date from the Invoices workspace. A resident can review the bill and download a PDF from the student dashboard.
- Cash reports remain pending until the owner confirms receipt; the owner can decline an incorrect report. Only confirmed cash and server-verified online payments update invoice balances and appear as completed payments.
- To enable Razorpay online checkout, configure `NEXT_PUBLIC_RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, and `SUPABASE_SERVICE_ROLE_KEY` in the local/deployed server environment. Configure the Razorpay webhook URL as `/api/payments/razorpay-webhook` for the `payment.captured` event, set the same webhook secret, and enable automatic capture in Razorpay. Do not expose the private keys in browser variables or commit them. Without these values, online payment is disabled; cash reporting still works.
- Confirm the deployment has applied all migrations and enabled the `pg_cron` extension. Verify the `monthly-resident-rent-invoices` cron job in Supabase Cron before relying on scheduled billing.

## Database foundation

The initial migration covers profiles/owners, properties, floors, rooms, beds, students, occupancy history, reservations, billing, payments, complaints, notice/checkout records, expenses, staffing, visitors, food, documents, notifications, integrations, subscriptions, audit logs, and scheduled-job history. It enforces unique active occupancy for each bed and resident, uses integer paise for money, and enables RLS. Owner policies are active; fine-grained staff permissions and remaining feature workflows still need their application/server implementation before production use.

For safety, ordinary public signup creates an isolated PG_OWNER tenant. Student signup requires a one-time invitation token that is generated by an owner-authorized database function, bound to the student's email, stored only as a hash, and consumed by the auth trigger. SUPER_ADMIN and staff privileges must only be assigned by trusted server-side code. Do not expose service-role credentials.

## Security notes

The Supabase service-role key is server-only and must never be exposed to the browser. Multi-tenant authorization, database migrations, and RLS policies are part of the upcoming backend phase; do not treat client-side authentication alone as an authorization boundary.
